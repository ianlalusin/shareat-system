### ⭐ Why BOTH keys, and why changing only the first would have taken the whole app down

`systemTransaction()` and `authTransaction()` resolve to `SYSTEM_DATABASE_URL ?? DATABASE_URL`
(`packages/db/src/client.ts:97`). With `SYSTEM_DATABASE_URL` unset — which is how production stood
until today — they are **byte-for-byte the same connection as `transaction()`**. So tightening
`DATABASE_URL` alone would have tightened the auth door and the scheduler door with it, and bible
§13 row 194 / DEF-288 record exactly what that costs: PIN sign-in returns *"that PIN is not valid
for this store"*, every authenticated request returns *"Not signed in"*, and the ETL tables (FORCE
RLS, **zero policies**) become unreachable. Not degraded — the whole application unusable, at once.
⚠️ It fails CLOSED, so it is an availability wall and never a leak. That is the only reason this was
recoverable rather than a data incident.

### ⛔ THE CONSEQUENCE THAT WILL BITE: migrations on the box must use the ADMIN string

`npm run db:migrate` reads `DATABASE_URL`. `shareat_app_prod` is `NOCREATEDB NOCREATEROLE` and owns
no table, so it **cannot run a migration** — correctly, and by design. A deploy or a manual migrate
that inherits the file as written will fail with a permission error.

Run migrations against the release you actually mean to migrate — not `/srv/shareat`. That symlink
is swapped LAST, only after a successful migrate (`deploy.yml`, `mv -Tf /srv/shareat.new
/srv/shareat`), so on the one deploy this recipe exists for — the one that failed AT the migrate
step — it still points at the release BEFORE the failed one, and migrating through it silently
applies nothing while printing the same success line a real migration would (DEF-330, measured:
`Migrations applied in 231ms` for a no-op). Resolve the release explicitly instead, the same way
the deploy does, and verify with a count, not with the command's own output:

```bash
# Full ranked list first — eyeball that the top entry's timestamp matches the failed Deploy run
# you are recovering from (visible in its GitHub Actions log) before trusting the automatic pick
# below. If it does NOT match, STOP: something else has touched /srv/shareat-releases/ since, and
# "newest by mtime" is no longer "the one from that deploy".
ls -1dt /srv/shareat-releases/*/

RELEASE="$(ls -1dt /srv/shareat-releases/*/ | head -1)"
echo "Migrating release: $RELEASE"

# Same extraction and sanitizing deploy.yml's migrate step uses, copied in full rather than just
# the grep — DEF-196/DEF-203: this file has a documented history of CRLF line endings and a BOM on
# the box, so a decorated-but-present key must never be misread as absent, and a bare grep/cut
# would hand postgres() a connection string with a trailing \r during the exact incident where
# that looks like a credential failure instead of a whitespace one.
SYSTEM_DB_URL="$(grep -m1 '^SYSTEM_DATABASE_URL=' /srv/shareat-shared/.env.local | cut -d= -f2- || true)"
SYSTEM_DB_URL="${SYSTEM_DB_URL%$'\r'}"
case "$SYSTEM_DB_URL" in
  \"*\") SYSTEM_DB_URL="${SYSTEM_DB_URL#\"}"; SYSTEM_DB_URL="${SYSTEM_DB_URL%\"}" ;;
  \'*\') SYSTEM_DB_URL="${SYSTEM_DB_URL#\'}"; SYSTEM_DB_URL="${SYSTEM_DB_URL%\'}" ;;
esac
if [ -z "$SYSTEM_DB_URL" ]; then
  echo "SYSTEM_DATABASE_URL is missing or empty in /srv/shareat-shared/.env.local — refusing to run." >&2
  exit 1
fi

cd "$RELEASE"

echo "Before:"
DATABASE_URL="$SYSTEM_DB_URL" node -e "require('postgres')(process.env.DATABASE_URL,{max:1}).unsafe('select count(*)::int as n from drizzle.__drizzle_migrations').then(r=>{console.log(r[0].n);process.exit(0)}).catch(e=>{console.error(e);process.exit(1)})"

DATABASE_URL="$SYSTEM_DB_URL" npm run db:migrate

echo "After (must equal the journal count below):"
DATABASE_URL="$SYSTEM_DB_URL" node -e "require('postgres')(process.env.DATABASE_URL,{max:1}).unsafe('select count(*)::int as n from drizzle.__drizzle_migrations').then(r=>{console.log(r[0].n);process.exit(0)}).catch(e=>{console.error(e);process.exit(1)})"

echo "Journal entries:"
node -e "console.log(require('./packages/db/migrations/meta/_journal.json').entries.length)"
```

A `Migrations applied` line proves nothing on its own — DEF-330's own case printed it for zero

⚠️ **Do not "fix" this by giving `shareat_app_prod` DDL rights.** A role that can `ALTER TABLE` can

## Restores and replica mode (T-354)

DEF-487: 18 history-guard triggers (append-only / posted-immutable / frozen / commit-once /
terminal tables — `packages/db/src/triggers/registry.ts` names all of them) are `ENABLE ALWAYS`
since migration 0168, so they keep firing under `session_replication_role = 'replica'` — the mode
logical-replication apply workers use, and the classic hand-rolled-bulk-load trick ("turn off
triggers"). Three things to know before touching this database directly:

- **A full restore (`pg_dump` / `pg_restore`, or a managed physical backup) keeps `ENABLE ALWAYS`.**
  Triggers are created in the post-data section, after the rows load, and `pg_dump` records each
  trigger's firing mode — a full restore reproduces the same protection, nothing to redo.
- **A data-only restore needs `pg_restore --disable-triggers`, run as the table owner, and that
  deliberately bypasses every history guard — ALWAYS ones included.** It is the correct tool for
  loading rows into a database that has none yet (no risk of overwriting real history because there
  is none to overwrite). Restore this way **only into an empty database.** Restoring data-only into
  a database that already holds live rows disables the guards for the whole operation.
- **Never run `SET session_replication_role = replica` against a live database.** The 18 history
  guards keep firing under it (that is what 0168 fixed), but the other 39 triggers — every
  origin-mode derivation and bookkeeping trigger, e.g. the store money-account seeding — silently
  stop for everything that session does, so rows it writes skip their derived side effects. There
  is no legitimate reason to set it here: no application or ops path does (this codebase runs no
  logical-replication subscriber and no bulk loader); the only hit in the tree is the T-354 test
  that proves the 18 guards fire under it.

```sh
  # shareat-month-end.service via Unit=. Skip any timer with no matching service file.
  [ -e "/etc/systemd/system/$u.service" ] && sudo systemctl start "$u.service"
done

journalctl -u shareat-month-end.service -n 50    # repeat per unit
```

⚠️ **`systemctl enable` without `--now` arms it for the next boot and not for today.** That single
missing flag is the shape of every failure in the table at the top of this file.

## ⭐ How you find out it stopped — without another cron

`scheduler_runs` records every run, including one that did nothing. But a table nobody opens is not
an alarm, and a watchdog that is itself scheduled can die with the thing it watches.

**So the real alarm reads the DATA, not the scheduler.** The `openShiftsStale` finding on
`/findings` fires when a shift has been open more than two days, and it is derived on read — it is
true whether or not the sweep ever ran, and it is `hard` severity, so it blocks a period close.

⛔ **If that finding keeps appearing, the timer is not installed.** That is the whole design.

### ⚠️ The exception: `finding_observation` has no such alarm, and cannot have one

The trick above works because the sweep's *absence* leaves a trace in data that something else
derives. **T-214's observation job is the thing that creates the trace**, so its silence looks
exactly like a quiet week: no new occurrences, nothing overdue, a scorecard that simply stops
moving. There is no derived finding that fires because the recorder stopped recording.

What is available instead, and it is weaker on purpose rather than by oversight:

- `/findings/scorecard` prints **"record began on \<date\>"** from `min(opened_on)`, and every
  occurrence carries `last_seen_on`. A `last_seen_on` more than a day or two behind today means the
  job has stopped — visible to anyone who opens the page, invisible to anyone who does not.
- `scheduler_runs` holds a row per run, so `select max(started_at) where job = 'finding_observation'`
  answers it exactly.

⛔ **Do not "fix" this by adding a detector that reads `finding_occurrences`.** Nothing in the
detection path may read that table — it is an observation log, not finding state, and the moment a
detector consults it, T-135's rule is broken and v1's suppression defect is back. An integration
test asserts this by deleting every row and re-reading the feed. The gap is real; closing it this
way costs more than it buys.
