| Job | Command | Cadence | Why that cadence |
|---|---|---|---|

## ⭐ Standing up an organization on production — `npm run bootstrap-org` (T-228)

⛔ **This is the one command here that is NOT a job, must NOT be given a systemd unit, and is run
by a person — Ian — not by an agent.** Everything else on this page is a timer. This is a one-shot
that writes to the live database and prints a live credential once.

**Why it exists:** nothing in this codebase had ever created an organization (DEF-195). Production
is live and migrated and held **zero** organizations, which is why
`shareat-finding-observation.service` exits 1 nightly with *"no orgs were processed"*. That failure
is correct; this is the fix.

### The invocation

```sh
# On the droplet, from /srv/shareat, with the app's own .env.local in place.
# ⚠️ DRY RUN FIRST — without --confirm it prints the plan and writes nothing.
npm run bootstrap-org -- --code=SHAREAT_OPC --name="SHAREAT OPC"                          --admin="<the person's real full name>"                          --store-code=LIPA --store-name="SharEat Lipa"

# Then, once the printed plan says what you expect, exactly the same line plus --confirm:
npm run bootstrap-org -- --code=SHAREAT_OPC --name="SHAREAT OPC"                          --admin="<the person's real full name>"                          --store-code=LIPA --store-name="SharEat Lipa" --confirm
```

| Guard | Behaviour |
|---|---|
| **No defaults** | Every argument except `--pin` is required. There is no `SHAREAT_OPC` fallback in the code — the example above is documentation, not a default |
| **`--confirm` required** | Without it: prints the plan, writes nothing, exits 0. The dry run is the default |
| **Duplicate code** | Refused, exits 1, writes nothing. A second run is a no-op, not a second org |
| ⛔ **NOT guarded on database name** | The inverse of `dev-seed.ts`, deliberately. `dev-seed` refuses anything but `*_dev` because it must never reach production; this one is *for* production |
| **One transaction** | Org, chart of accounts, expense categories, first admin, first store, its default room, that admin's store scope, and the PIN. All of it, or none of it |

### ⚠️ The PIN is shown ONCE

The script prints the PIN to **stdout, exactly once**, and only its hash is stored — it is not
recoverable, by anyone, from anywhere. Supply your own with `--pin=NNNNNN` or let it generate one
(`crypto.randomInt`, six digits).

⛔ **This is why it must never be given a systemd unit.** Every `*.service` on this page redirects
stdout to `/var/log/shareat/*.log`; under a unit, that credential would be written to a log file and
would stay there. Run it by hand, read the PIN, sign in, change it from the app.

### What it deliberately does NOT do

- **No second store.** It creates exactly one, because one is what `setPin` requires. **SharEat
  Malvar and the rest are created afterwards through `/admin/stores`** — the supported path, and a
  real production smoketest of T-222 on its first day.
- **No sales channels, no items, no opening balances.** `/cutover` (T-134) owns opening balances;
  the rest are ordinary screens. ⚠️ A store with no sales channel has nowhere for a sales day to
  land — the store's readiness checklist says so, and that is the next thing to do after signing in.
- **No `super_admin`.** `admin` is what `manage_stores` and `manage_users` need, and it is also what
  `createStore`'s scope fan-out grants against — a `super_admin` first admin would end up with no
  store scope row and nowhere to land. Item approval (T-148) is a later, deliberate `/admin/users`
  action.

⭐ **Ian runs this himself.** `docs/IAN-SETUP-CHECKLIST.md` §4b's principle — no standing production
credentials through an agent — covers this as surely as it covers provisioning.

## ⛔ FIRST — getting `docs/ops` onto the droplet, because the pipeline never ships it

**DEF-194, 2026-09-06.** This section used to open *"after `docs/ops/provision.sh` has run once"*
and **never said how `docs/ops` gets there**. It does not get there:
`.github/workflows/deploy.yml:82` ships `apps/erp/.next`, `packages`, `scripts`, `node_modules` and
the two manifests — **no `docs/`, ever**. So `/srv/shareat/docs/ops/provision.sh` is a path that has
never existed on any droplet, and an instruction naming it cannot work.

⚠️ **It was written into a handoff in exactly that form and Ian ran it**, in a Windows shell, which
failed twice over — wrong path *and* wrong host, because the step never said it happens over SSH.

⭐ **`provision.sh`'s own header had the answer the whole time**, along with the reason: it installs
the `*.service`/`*.timer` files that live **beside** it, so **the directory travels, not the file.**

```sh
# From the repo on a machine that can reach the droplet:
ssh root@<DROPLET_IP> 'rm -rf /root/shareat-ops'     # DEF-194: scp -r into an EXISTING dir nests
scp -r docs/ops root@<DROPLET_IP>:/root/shareat-ops
ssh root@<DROPLET_IP> 'bash /root/shareat-ops/provision.sh'
```

⛔ **The `rm -rf` line is not optional — it is DEF-194's actual root cause.** On 2026-09-06 the
corrected `scp -r` was run against a `/root/shareat-ops` left over from 4 Sep; `scp -r` into an
existing directory **nests** (`/root/shareat-ops/ops/`) rather than merges, so `provision.sh` ran the
two-day-old copy, reported success, fixed nothing in `/srv`, and installed 7 of 9 units. A stale copy
of a provisioning script is more dangerous than none, because it succeeds.

⚠️ **Omit the domain argument once the site is already live.** Passing it rewrites
`/etc/caddy/Caddyfile` and reloads Caddy on a working site for no benefit; omitting it still creates
the directories, fixes `/srv`'s group-write and installs every unit.

⛔ **Every future "arm the timer" instruction starts here.** `provision.sh` is the only thing that
installs unit files, and the pipeline ships no `docs/` — so a new job's unit reaches the box by this
route or not at all. Three jobs have now shipped unarmed, and this missing step is part of why.

## Installing everything (after `provision.sh` has run once, per the section above)

`provision.sh` installs all nine unit files (`shareat-erp.service` +
four `.service`/`.timer` pairs) via `systemctl daemon-reload`, but does **not** enable or start
them — there is nothing to point them at until the first deploy lands. After `deploy.yml` has run
successfully at least once:

```sh
sudo systemctl enable --now shareat-erp.service
sudo systemctl enable --now shareat-firestore-relay.timer
sudo systemctl enable --now shareat-attendance-sweep.timer
sudo systemctl enable --now shareat-month-end.timer
sudo systemctl enable --now shareat-finding-observation.timer
```

**Verify each is actually armed** — this is the step that has historically never been done:

```sh
systemctl list-timers   # NEXT and LEFT must be populated for all FOUR timers
sudo systemctl start shareat-attendance-sweep.service   # run each job once, now
sudo systemctl start shareat-firestore-relay.service
sudo systemctl start shareat-month-end.service
sudo systemctl start shareat-finding-observation.service
journalctl -u shareat-attendance-sweep.service -n 50    # repeat per unit
```

⚠️ **`systemctl enable` without `--now` arms it for the next boot and not for today.** That single
missing flag is the shape of every failure in the table at the top of this file.

Cost an hour on 2026-09-06 as two "unrelated" symptoms | `rm -rf` the destination first (the block above does), or name one that cannot pre-exist |
| **UTF-8 BOM in `.env.local`** (DEF-196) | `. .env.local` fails with `line 1: <U+FEFF>DATABASE_URL=...: No such file or directory` — and **echoes the whole line, password included** | Never write that file from a Windows editor or `Set-Content`; check with `head -c3 .env.local \| xxd`. | **`cat >>` onto a file whose last line has no trailing newline glues two settings into one** (DEF-203) | `APP_TIMEZONE=Asia/ManilaDATABASE_URL=postgresql://…` as one 184-character line. `cut -d= -f1` still prints `APP_TIMEZONE`; `cat -n \| cut -c1-30` hides the tail; only `grep -c sslmode` returning 2 disagreed — believe the disagreement | Build the file in a **staging copy** under `/root`, verify with `grep -c ^KEY` per key plus a value fragment, then `cp` over the live file. `printf '\n' >>` before any append. `cat -n`, never `nl`, when cross-referencing `grep -n` |

## ⭐ How you find out it stopped — without another cron

`scheduler_runs` records every run, including one that did nothing. But a table nobody opens is not
an alarm, and a watchdog that is itself scheduled can die with the thing it watches.

**So the real alarm reads the DATA, not the scheduler.** The `openShiftsStale` finding on
`/findings` fires when a shift has been open more than two days, and it is derived on read — it is
true whether or not the sweep ever ran, and it is `hard` severity, so it blocks a period close.

⛔ **If that finding keeps appearing, the timer is not installed.** That is the whole design.

### ⚠️ The exception: `finding_observation` has no such alarm, and cannot have one

The trick above works because the sweep's *absence* leaves a trace in data that something else
derives. **T-214's observation job is the thing that creates the trace**, so its silence looks
exactly like a quiet week: no new occurrences, nothing overdue, a scorecard that simply stops
moving. There is no derived finding that fires because the recorder stopped recording.

What is available instead, and it is weaker on purpose rather than by oversight:

- `/findings/scorecard` prints **"record began on \<date\>"** from `min(opened_on)`, and every
  occurrence carries `last_seen_on`. A `last_seen_on` more than a day or two behind today means the
  job has stopped — visible to anyone who opens the page, invisible to anyone who does not.
- `scheduler_runs` holds a row per run, so `select max(started_at) where job = 'finding_observation'`
  answers it exactly.

⛔ **Do not "fix" this by adding a detector that reads `finding_occurrences`.** Nothing in the
detection path may read that table — it is an observation log, not finding state, and the moment a
detector consults it, T-135's rule is broken and v1's suppression defect is back. An integration
test asserts this by deleting every row and re-reading the feed. The gap is real; closing it this
way costs more than it buys.
