## Findings (ranked)

**F1 — HIGH · S7 builder paths, K5, §1 item 5. The item split is now T-391's job, and the org code must match stores.csv.**
Evidence: T-391 R6/R7 (`docs/tasks/391-production-master-data-load.md:106-107,438`) already load PG with
`master-data run --org <PG> --org-code <code> --stores <PG code> --actor <a PG person>`. `assertRunTarget` refuses unless
`organizations.code` equals `--org-code` (`packages/etl/src/master-data/store-map.ts:87-94`). Today stores.csv uses the placeholder `PADRE_GARCIA`.
In Ian's org, parties that point at PG are held with reason `franchise` (`parties-plan.ts:231-253`). In a PG run, PG's v1 supplier that mirrors
the commissary links to an own store of ANOTHER org, so `own` is null (`:239`). It would be imported as a plain supplier, and S7 also creates one, so it would exist twice.
Fix: delete `scripts/import-items.ts --v1-store` from S7, and delete K5. Add to S7:
"(1) `onboard-franchise --code` MUST equal stores.csv's PG `org_code` (today `PADRE_GARCIA`), and the store code MUST equal its `store_code`;
(2) order: onboard CLI first, then `master-data run --org <PG> --actor <Ian's PG person>`. The CLI's PG-side supplier and Ian-side customer
take the v1 names of the commissary-mirror supplier and the PG AR customer, so the planner matches them and does not create them again. A new leg O8 covers this:
after onboarding, a PG dry run plans 0 new suppliers named like the commissary."
