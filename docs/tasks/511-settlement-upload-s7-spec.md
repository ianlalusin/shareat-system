## Rulings
1. **Who may approve.** `record_ar_collection` at the line's store (design J; weak fit accepted in S6). Separation of duties (decision 10): refused if the actor uploaded EITHER of the line's uploads (Grab: source and payout upload; Foodpanda: the invoice upload), unless the actor is an admin, tested exactly as `reopenDay` tests it (`override_period_lock`, `review.ts:429`). In a one-admin shop the admin is exempt: that is the accepted default, not a gap. Refusal sentence in plain words, no other store named.
2. **One transaction, fixed order** (design 17(7), discovery): lock channel (`advisoryLocksRepo.lockSettlementChannel`, as ingest) → read the line `forUpdate` and re-check pending + current → authorize + uploader rule → re-run `dayBlockers` INSIDE the tx → `correctPlatformSales` (skipped when the file figure equals the booked figure) → `recordChannelSettlement` → `markBooked` (compare-and-set pending+current → booked, decided_by/at, settlement_id) → audit. Any throw rolls back all of it.
3. **Mapping** (extend `lineToSettlementInput`, one place): `reference` = Grab settlement id / Foodpanda invoice number (new `payoutReference` on the line input, max 120 per field rules); `salesDayId` = the live verified day (as `correction.ts:66`); `settledOn` = `willPostOn ?? salesDate` (never post into a closed period; payment-arrival dating and deferrals stay slice 8); `acknowledgeDifference` only from the approver's typed reason; `settleChargeIds` and the `netDeposited` reduction per ruling 6. ONE clock: the tx's Manila date (`manilaToday(tx)`) is passed into `dayBlockers` (add an optional `today` param, default as now) so "will post on X" and the actual date cannot differ.
4. **Blockers are one list** (design: the screen and approve call the same function). Add to `dayBlockers`: `loan_leg_problem` (the text of `loanLegsForLine().blocker`; S6 required it, today only `.legs` is read, `day-checks.ts:169`); `nothing_to_settle` (order value 0: the payout cannot post, owner handles it by hand; plain words); `sales_day_not_posted` (verified but no journal entry, so `correctPlatformSales` cannot run: say "Staff recorded no sales for this day, so the file figure cannot replace anything yet"; accepted limit); `period_charge_unbooked` (ruling 6). Messages privacy-safe: reuse the existing loan wording, a test asserts no other store's name or balance appears.
5. **Difference past tolerance and the typed reason.** The preview before approving runs before the correction, so it cannot tell. Approve therefore runs correction first, then previews in-tx; if the settlement then needs an acknowledgement and no reason was supplied, it throws a typed refusal `NEEDS_REASON { difference, sign }`, the whole tx rolls back (the correction too), and the screen re-asks with a reason box (S7b). The correction's own reason is generated plain text ("Platform file figure for {date} (upload {short id}) replaces the staff figure"), within `PLATFORM_CORRECTION_RULES` (plainText, ≤500); the approver types only the acknowledgement reason.
6. **Period charges and netting** (Foodpanda only). A charge is booked by its own action first (S7b button; `postPlatformCharge`, same permission and uploader rule). The platform nets it from the invoice payout, and staged `net_payout` excludes it, so the CARRIER day = the latest-dated current day line of the same upload. At the carrier, approve passes `settleChargeIds` = every posted, un-netted charge of that upload and sets `netDeposited = staged net_payout − C`. Blocker `period_charge_unbooked` on the carrier while any charge of its upload is staged but not posted. A charge from a fee-only invoice (no days) is posted and stays a 1220 credit until slice 8 (accepted S6c limit). If the carrier is rejected the charge stays a credit.
7. **Void returns the day to pending.** `voidChannelSettlement` (and only it) additionally, in the same tx, moves a day line that is current and `booked` with `settlement_id` = the voided settlement back to `pending` (decided_* cleared, settlement_id null, audited `settlement_day.unbooked`), so a plain void is not a dead end. A non-current line stays booked as history. Re-approve is safe: the sales correction is idempotent per line, charge links stop counting through the voided parent (S6c).
8. **Approval order** stays (`earlier_day_open`). No "approve all clean days" here (named follow-up; the 15-minute target may want it).
9. **Audit** (catalogue +2, ceilings 250 → 252 in t402/t453): `settlement_day.approved` (money, high, store scope: actor, line id, settlement id, correction id or none, charge ids, upload ids, reader version, difference reason presence) and `settlement_day.unbooked`.

## Worked examples (numbers go in the tests and POSTING-PATTERNS)
**Grab day, correction first.** Staff 10,000.00; file order value 11,000.00; commission 2,200; platform fee 100; loan leg 500; payout 8,200 (= 11,000 − 2,300 − 500). Approve: (1) Dr 1220 1,000 / Cr 4150 1,000 (party channel, dated the sales day); (2) settlement: Dr bank 8,200, Dr 6400 2,300, Dr 2400 500 / Cr 1220 11,000, difference 0, no acknowledgement. Negative control: skip the correction → owed 10,000, difference −1,000 inside tolerance (max(50, 10% of 11,000)) → books 6420 1,000 silently and leaves 1,000 on 1220.
**Foodpanda week with a period charge.** Invoice INV-1, days D1 gross 9,000 (fees 1,800, net 7,200), D2 8,000 (1,600, 6,400), D3 10,000 (2,000 incl. the weekly platform fee, net 8,000); an unrecognised Appendix B charge net 100 + VAT 12 = 112, booked first (Dr 6400 112 / Cr 1220 112). D1, D2 approve as plain days. D3 is the carrier: `settleChargeIds [c]`, `netDeposited` 8,000 − 112 = 7,888 → Dr bank 7,888, Dr 6400 2,000 / Cr 1220 9,888, difference 0. Bank total 7,200 + 6,400 + 7,888 = 21,488 = the invoice total; 6400 holds the charge once (112) plus day fees.
