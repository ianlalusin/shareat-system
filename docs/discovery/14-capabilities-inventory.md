## Capabilities with no home in the plan

Every row below is genuinely **NOT PLANNED** — not named in `PROJECT_BIBLE.md` §10's phase table, and not obviously subsumed by one of Phase 3's generic bullets ("Items, locations, stock ledger, receiving, transfers, usage, wastage, counts, weighted-average valuation, COGS postings"). This is the primary deliverable of this report.

1. **The entire commissary ↔ branch order pipeline (§O, ~24 capabilities).** Order → fulfil → dispatch → confirm-receipt (which posts BOTH stores' books at once) → discrepancy resolution → settle/defer → repair/backfill. This is not a small feature — it is a full second transactional domain that currently sits at the intersection of Phase 2 (AR/settlements) and Phase 3 (inventory), touching neither phase's stated deliverables explicitly. **What breaks if never built:** every store that operates as a branch of a commissary (which per `01-data-model.md`'s real production numbers is most of the 7-store fleet) has no way to order from, receive from, or settle with its supplier-of-record. The commissary has no way to dispatch or bill. This is not a peripheral module — for a branch store, it is how inventory gets replenished at all. If ERPv2 launches with Phase 3 (generic inventory) but no commissary-order phase, branch stores cannot restock through the new system on day one.
2. **POS item mapping + POS usage pull (§L).** The mechanism that keeps on-hand inventory honest against actual sales (as opposed to manual usage entry). Not named in any phase. **What breaks:** without it, every sale silently fails to decrement stock unless a manager hand-enters usage for every sold item every day — which is exactly the manual burden this feature exists to remove. Inventory numbers drift from day one of cutover.
3. **Meat production / slicing conversion + slicer payroll (§M).** Named nowhere — Phase 3's "usage...COGS postings" is generic enough to arguably cover the stock-conversion half, but the slicer-payroll half (a real, separate compensation stream with overlap/gross-drift/duplicate guards, entangled with `liability__salaries_payable`) belongs to Phase 5 and isn't named there either. **What breaks:** any store that runs a meat-slicing operation loses both its stock-conversion tracking and its slicer pay computation.
4. **Order/channel wastage disposition + settlement-match (§N).** Distinct from raw-stock wastage (which Phase 3 does name generically). This is order-economics reconciliation against FoodPanda/Grab payouts — dispute, 15-day auto-charge backstop, settlement-match. **What breaks:** channel-order losses stop being tracked or recovered at all; the 15-day backstop (which currently prevents indefinite drift) has no replacement.
5. **Branch low-stock auto-order (§D).** A specific automation (branch usage/wastage post → threshold breach → auto-draft a commissary order line). Small in isolation, but its absence means the low-stock signal (which IS planned, generically) never turns into an actual replenishment action without a human remembering to check the low-stock list.
6. **Supplier returns as a first-class record (§G).** Arguably subsumed by Phase 3's "receiving," but the specific documented CHOICE (stock+audit trail only, deliberately NOT touching AP/journal) is a scope decision that needs Ian's explicit re-confirmation given ERPv2's stricter stock↔GL coupling (§16.11) — silently porting v1's compromise would be porting a known gap forward.
7. **Cookbook (presentation recipes) — actually IS planned** (Phase 7, named explicitly). Listed here only to distinguish it clearly from item 3's production recipes, which are NOT named and are easy to conflate with it during scoping.
8. **The mobile (Flutter) inventory API bridge (§P).** Eight authenticated REST routes under `/api/{inventory,meat,production,deliveries}/*` give a dedicated handheld app the same receive/void/count/threshold/transfer/adjust/cook capabilities the web UI has — not named anywhere in the bible (the only "hot lane"/offline discussion in §5 is scoped to the attendance clock terminal, not inventory). **What breaks if never built:** if this app is in active use on the floor (project memory references a `project_flutter_inventory_apk` doc — confirm usage with Ian before assuming it's abandoned), stockroom staff lose the ability to receive, count, or transfer stock from a handheld at the point of work and are forced back to a desktop/laptop workflow, which is exactly the friction a mobile client exists to remove.
9. **A previously-built AI reorder-alert system that no longer exists in code.** See §D — `archive/TODO-smart-reorder.md` is stamped "DONE," `firestore.rules` still carries live rule blocks for its two collections naming a since-deleted `reorder.actions.ts`, and the item master still exposes UI fields (`reorderPoint`/`reorderQuantity`) that fed it. This is not a "not planned" gap in the usual sense — it is evidence of a **regression**: real functionality (14-day projection, seasonality, AI recommendations, an alerts dashboard) that existed and was removed, leaving only debris. Ask Ian why before either reviving the design or writing it off.

## Intent worth preserving

Business rules encoded in code that a schema-only rebuild would lose:

- **Meat re-categorization guard is a real-incident fix, not a nicety.** Blocking (not warning) a slab→non-slab category change while sliced children still point at it exists because of a specific, named production incident (Lipa's `Beef Forequarter/regular`, 3 orphaned children, 7 corrupted production records). Do not soften this to a warning. (`meat-product-validate.ts:76-89`)
- **Unit-conversion refusal-to-guess.** `resolveRecipeUnitConversion` converts ONLY g↔kg and ml↔ltr; every other pairing (pcs↔pack, pcs↔box, kg↔ltr) returns `null` and the caller MUST block, because those need a per-item factor that "guessing one here would deduct the wrong quantity forever." (`recipe-units.ts:53-56`)
- **Receiving parks undecided lines in "Receiving," never guesses a room; falls back to the default room only if no Receiving location exists at all — stock is never silently lost.** (`receive-allocation.ts:14-22`)
- **Over-receipt is allowed, but only with an explicit flag AND manager/admin — never a silent cashier bypass.** A deliberate trust-boundary design, not an oversight. (`delivery.actions.ts:450-474`)
- **Duplicate-delivery detection is advisory, WARN-never-BLOCK, on principle** — legitimate double-drops and bulk buys are normal; only the operator holding the physical receipt can tell a re-key from a real second delivery. (`delivery-duplicate-risk.ts:1-13`)
- **A usage record labeled "transfer" is rejected outright**, because the usage flow only ever writes an OUT leg — a mislabeled transfer silently destroys stock rather than moving it. Shared client+server guard, not UI-only. (`reserved-usage-categories.ts`)
- **Count-session freeze fails CLOSED on malformed data** (missing/non-array `locationIds`, unknown status → never frozen) because this predicate gates every other inventory writer — a defensive default direction worth restating explicitly. (`count-freeze.ts:22-31`)
- **Long-haul transfer reservation (`reserved`) is destination-side, dispatch-set, receive-resolved, and a void must NOT double-release it if the transfer was already received** — an easy double-release bug if the reversal doesn't branch on prior status. (`stock-transfer.actions.ts:396-425`)
- **Meat/general balance increments must happen INSIDE the write transaction, never pre-checked outside it** — two concrete, named historical bugs (a meat-balance negative-drift and a −20kg slab-drift) both trace to a pre-transaction balance read that a concurrent post could race past. `FieldValue.increment` is not idempotent; read-then-increment inside the same transaction is the only safe shape. (`meat-usage.actions.ts:310-323`; `production.actions.ts:231-247`)
- **Ledger-gap tolerance on void: proceed and report, never invent or get stuck.** When a void's expected ledger leg is missing, the reversal is still computed from the RECORD's own fields (always correct) and the gap is surfaced (`voidLedgerGaps`) rather than either fabricating a leg that was never observed or refusing the void and leaving the record permanently stuck. (`production.actions.ts:951-967`)
- **Slicer payment freezes the production records it covers.** A live (non-voided) slicer payment blocks editing or voiding any production record it was computed from — because the payment's `totalPayment` is FROZEN at generate time while the underlying records stay editable, and once the period's lump sum recognizes the cost there is no route back. (`production.actions.ts:64-114`)
- **Confirm receipt posts BOTH stores' books at RECEIVED quantity, at receipt time — never at fulfilled/dispatched quantity.** This single rule is what makes branch AP and commissary AR agree by construction instead of needing retroactive discrepancy correction. (`branch-order-receive.actions.ts:56-80`)
- **Provisional recognition, atomic flip.** A clean receipt is stamped `pending_variance` BEFORE the cross-store AR transaction runs, flipped to `recognized` only inside it — so a failed second-store posting leaves the order recoverable rather than stranded as recognized-but-unbilled. This is the specific pattern that makes the "Firestore can't span two stores" limitation survivable; the underlying invariant ("never recognize revenue you haven't successfully posted AR for, never leave a clean receipt un-recoverable") must survive the move to a real cross-table Postgres transaction even though the two-phase workaround itself can be deleted.
- **Auto-book AP authority and receipt-confirm authority must be ONE shared definition, never two.** The concrete, dated, dollar-figured incident (Banay-Banay BO-BNY-2607-0011, 2026-07-23, ₱12,184.71 in silently-unbooked AP) exists specifically because these two gates drifted apart. `canBookBranchDeliveryExpense` now backs both; preserve the single-definition discipline, not just the current gate values. (`commissary-delivery-expense.actions.ts:283-295`; `autobook.ts:27-56`)
- **"Max of last two receives" pricing basis** prevents one cheap delivery lot from crashing the branch price below what an earlier, still-in-stock expensive lot actually cost. (`pricing.ts:98-103`)
- **The 15-day wastage auto-charge clock is uniform across disputed and undisputed records** — a prior exemption for disputed records was deliberately removed so a dispute nobody resolves doesn't become a permanent way to dodge the backstop. (`wastage.actions.ts:1131-1136`)
- **A shipped server action is not a shipped feature.** Twice in this domain (supplier returns, count-session freeze) a fully-built, permission-gated, transactional server action sat with zero UI callers for seven weeks — in the freeze case, a genuine landmine (a session created by any other route would have frozen a location permanently for non-admins, with no way to close it). When verifying ERPv2 parity against v1, check for a live route, not just an exported action. (`INVENTORY_GAPS.md:61-78,120-135`)
- **`itemReorderPolicies`/`reorderAlerts` are dead schema, not a design to port.** The real, live reorder mechanism is a single `lowStockThreshold` field plus a summed-on-read low-stock query — simpler than the data-model doc's collection list implies. Do not build a policy-object reorder system; build the threshold-based one that's actually in production.
- **A shipped AI reorder-alert system apparently existed and was later removed** (see §D, "no home" item 9) — treat this as a regression to investigate with Ian, not a feature request to scope fresh.
- **The wastage reason taxonomy is a fixed, shared enum, not free text** — one canonical list used across item-usage, meat-usage, and general-inventory specifically so "reports can aggregate 'spoilage' or 'theft' across all item kinds without per-module string normalization": `spoilage`, `expiry`, `damage_storage` (in storage), `damage_handling` (in handling), `prep_loss`, `overproduction`, `theft`/shrinkage, `quality_reject`, `customer_return_unsellable`, `other`. Preserve as a real enum/lookup table, not a free-text column — the whole point was to stop each module inventing its own spelling. (`src/lib/financial/inventory/wastage-reasons.ts:1-34`)
- **The delivery-shortage reason taxonomy is a separate, smaller enum** from wastage — a short-received line is classified `not_received` (auto-set, excluded from the manual picker), `supplier_short`, `damaged_in_transit`, `damaged_on_arrival`, `quality_reject`, `count_correction`, or `other`. Distinct from wastage reasons because a shortage is a supplier-relationship signal (feeds supplier performance conversations), not a stock-loss classification. (`src/lib/financial/inventory/shortage-reasons.ts:1-33`)
- **Wastage is two unrelated systems sharing one word.** `wastages/{id}` (`wastage.actions.ts`) tracks ONLY `source:'order'` — a cooked menu item lost to FoodPanda/Grab/dine-in, an accountability/GL workflow with **no stock movement at all**. The type comment on `WastageSource` names `source:'inventory'` (raw-material spoilage that decrements stock) as **"Phase 2"** — i.e., v1 itself planned a second wastage system and never built it; every "raw stock wastage" capability actually lives in the unrelated `WASTAGE_REASONS`-tagged usage-record path (`general-inventory.actions.ts`/`meat-usage.actions.ts`), a completely different collection with a completely different lifecycle. Do not let "wastage" in a requirement default to the wrong one of these two systems. (`src/types/wastage.ts:1-16`; `wastage.actions.ts:4-7`)
